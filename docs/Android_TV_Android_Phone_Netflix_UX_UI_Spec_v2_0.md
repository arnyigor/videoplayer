# Android TV + Android Phone / Tablet — единая UX/UI-спецификация сервиса фильмов и сериалов

**Версия:** 2.0 (единая спецификация, TV v1.1 сохранена)  
**Дата:** 20 октября 2026  
**Формат:** практическое руководство для Android TV, Android Phone, планшетов и складных устройств  
**Продукт:** Netflix-подобный каталог фильмов и сериалов (не видеохостинг пользовательских роликов)  
**Целевые платформы:** Android TV / Google TV (D-pad/OK/Back) и Android Phone/Tablet/Foldable (touch, IME, жесты, adaptive UI)  
**Рекомендуемый UI-стек:** Kotlin + Compose for TV (`androidx.tv:tv-material`) **и** Jetpack Compose Material 3 для mobile; общий domain/data/Media3

> Статус: проектные рекомендации и критерии приёмки. Это не копирование Netflix и не список обязательных требований Google. Конкретные размеры, тайминги и пороги ниже — **настраиваемые стартовые значения** с последующей проверкой на реальных устройствах.

## Карта документа

- **Часть I (разделы 1–17): Android TV.** Компоновка, фокус, D-pad, каталоги, сериалы, плеер, TV-тесты. Исходная TV-спецификация сохранена.
- **Часть II (разделы 18–33): Android Phone / Tablet / Foldable.** Мобильный UX, адаптивный Compose, плеер, общий проект/модули, синхронизация между TV и телефоном, тесты и очередность реализации.
- Все специфичные для Android TV указания ниже в части I относятся **к TV-оболочке**. Архитектуру модулей для **общего проекта** задаёт раздел 26, а не историческая структура в разделе 12.
- **Главное решение:** один каталог/история/профиль/правила проигрывания, но *разные* UI и контролы для пульта и touch.

# Часть I. Android TV / Google TV — основная спецификация

## 1. Что меняется по сравнению с универсальным видеоприложением

| Решение | Для видеохостинга | Для сервиса фильмов/сериалов — **выбираем** |
|---|---|---|
| Основная карточка | Превью 16:9 + автор и длительность | **Постер 2:3**, отдельный тип 16:9 для эпизодов и истории просмотра |
| Главная | Последние ролики, подписки, лента | **Продолжить просмотр**, Featured, рекомендации, новинки, жанры |
| Главный объект каталога | Видео | **Тайтл** (фильм или сериал), вложенные сезоны/эпизоды |
| Детальный экран | Описание ролика | **Карточка тайтла**; сериал = сезоны, эпизоды, рекомендации |
| Основная кнопка | Смотреть | **Продолжить** / **Смотреть фильм** / **Серия SxxExx** |
| История | Позиция видео | Позиция фильма **или конкретной серии**, статус сериала и последняя активность |
| Плеер | Стандартное видео | Медиа3 + **следующая серия**, intro/recap/credits (при наличии метаданных) |
| Пользователь | Нередко один аккаунт | Поддержка **профилей** в модели данных, даже если в MVP один профиль |
| Поиск | Видеоролики/каналы | Тайтлы, жанры, актёры (последние — при наличии достоверных метаданных) |

**Цель UX:** зритель должен быстро найти фильм/сериал, начать или продолжить просмотр, затем без усилий вернуться к следующей серии.

**Неприоритетно в первой версии:** трейлеры с автопроигрыванием на главной, сложные персональные алгоритмы, отдельный экран покупки, социальные функции, система оценок и отзывы, собственный экранный ввод текста.

## 2. Архитектура экранов и навигации

### 2.1. Основные разделы

Предлагаемый боковой список (свёрнутый rail слева, раскрывается при фокусе):

1. **Главная** — главный вход в сервис.
2. **Фильмы** — жанры, подборки, сортировки и все фильмы.
3. **Сериалы** — аналогичный каталог сериалов.
4. **Моё** — список просмотра, продолжить, история (с отдельными вкладками).
5. **Поиск** — на видном месте в верхней области rail или отдельным первым пунктом.
6. **Настройки / Профиль** — в нижней части rail.

Важно: **«Поиск» и «Профиль» могут быть отдельными действиями**, а не равнозначными вкладками. Не нужно дублировать «Продолжить просмотр» отдельным пунктом главной навигации: ряд на главной и вкладка в «Моём» достаточны.

**Решение по переключению разделов:** переключать **по OK**, а не автоматически при каждом перемещении фокуса. Оба поведения возможны; на первом этапе переход по OK снижает случайную подгрузку каталога и упрощает восстановление состояния.

### 2.2. Экранные маршруты

```text
App
├── ProfilePicker (только при нескольких профилях)
└── MainShell (sidebar сохраняет состояние)
    ├── Home
    ├── MoviesCatalog
    ├── SeriesCatalog
    ├── MyLibrary
    └── Search
        └── SearchResults

Дочерние маршруты поверх MainShell:
    TitleDetails(titleId)
    EpisodeDetails(episodeId)     [не обязателен, можно встроить в TitleDetails]
    Player(playableId, context)
    Settings
```

**Player** должен открываться полноэкранно, без sidebar; закрытие плеера возвращает именно на экран, из которого он был запущен. `context` содержит маршрут-источник и, при необходимости, выбранный сезон/эпизод — **не дублирует** сериализованную историю каталога.

### 2.3. Семантика Back

- В **плеере**, если поверх видео открыто меню: сначала закрываем меню, не выходим из просмотра.
- В плеере без дополнительного меню: возвращаемся на предыдущий экран и сохраняем позицию.
- На экране деталей: возвращаемся к **конкретной карточке** и позиции скролла.
- При открытой боковой панели: сначала закрываем панель.
- На корневом разделе: единая выбранная политика (например, повторный Back открывает системный выход/передаёт Back платформе); не показывать всплывающее подтверждение после каждого нажатия.
- Кнопку Home **не перехватывать**: её обрабатывает система.

## 3. Главная страница: рекомендуемый порядок контента

### 3.1. Порядок блоков

| № | Блок | Показывать при | Тип карточек |
|---|---|---|---|
| 1 | **Featured / Главная премьера** | Есть качественный backdrop и редакционная подборка | Один hero + до 3–5 переключаемых тайтлов |
| 2 | **Продолжить просмотр** | Есть начатый фильм/сериал | Горизонтальные 16:9 с прогрессом |
| 3 | **Для вас** | Есть данные рекомендаций | Постеры 2:3 |
| 4 | **Новинки** | Есть новые релизы | Постеры 2:3 |
| 5 | **Популярное** | Есть ранжирование | Постеры 2:3 |
| 6 | **Сериалы** | Есть каталог сериалов | Постеры 2:3 |
| 7+ | Тематические коллекции / жанры | Есть непустые коллекции | 2:3 или 1:1 для самой коллекции |

**В новом профиле**: нет истории просмотра — не показываем пустой блок. Вместо него показываем «Популярное» и «Новинки». Нельзя имитировать персонализацию надписью «Для вас», когда её нет.

### 3.2. Hero-блок

- На фоне — landscape/backdrop 16:9 или шире; затемнение под текстом.
- Слева: title/logo, год, возрастной рейтинг, жанр, краткий синопсис (2–3 строки).
- Первая кнопка: **«Смотреть»** или **«Продолжить»**.
- Вторая кнопка: **«Подробнее»**. Третья («Мой список») — только если помещается и востребована.
- **Не использовать обязательный autoplay со звуком.** По умолчанию нет авто-воспроизведения и авто-листания; дополнительные режимы — после проверки UX.
- Фокус внутри Hero **замораживает** любые запланированные переключения баннеров.
- Если нет backdrop: однотонная подложка + постер; если недоступен и постер — локальный placeholder.

**Вывод:** Hero должен ускорять старт просмотра, а не становиться отдельной рекламной областью.

### 3.3. Блок «Продолжить просмотр»

Карточка включает:

- Кадр/landscape-арт, либо постер как fallback.
- Название тайтла.
- Если сериал: `Сезон 2 · Серия 5` и, если есть, название серии.
- Индикатор уже просмотренной части **текущего видео**, а не всего сериала.
- OK запускает **продолжение**, а кнопка «Подробнее» доступна на экране деталей или через контекстное действие.

Нельзя показывать в этом ряду **несколько серий одного сериала одновременно** для одного профиля. Одна карточка сериала указывает на актуальную серию.

### 3.4. Горизонтальные ряды

- Использовать `LazyRow` внутри вертикального `LazyColumn`.
- Для каждого ряда — устойчивый `rowId`, для карточки — устойчивый `titleId`.
- Крайняя карточка ряда не должна «уводить» фокус в соседний ряд при повторном нажатии вправо.
- При переходе вниз выбирать ожидаемую карточку нового ряда: по близкой горизонтальной позиции или восстановленному индексу.
- Скролл выполняется предсказуемо, без прыжка на первую карточку после возвращения из деталей.
- Не запрашивать полные страницы каталога одновременно для десятков рядов: постепенная загрузка и кеш.

## 4. Каталоги «Фильмы» и «Сериалы»

### 4.1. Общий дизайн

- Верхняя область: заголовок + горизонтальные `FilterChip`.
- Быстрые жанры: «Все», «Фантастика», «Драма», «Комедия», «Триллер» и другие **из данных каталога**.
- Основной режим: сетка **постеров 2:3** с предсказуемой D-pad-навигацией.
- Вверху не более 1–2 строк элементов управления, остальная площадь — контент.
- Чипы: отдельное состояние `focused` и `selected`. Фокус **не должен** автоматически применять фильтр.

### 4.2. Сортировка и фильтры

**MVP:** жанр, год выпуска (по желанию), сортировка по популярности/новизне.

**Позже:** страна, рейтинг, продолжительность, HDR/4K, «Только доступное» (если такие метаданные есть).

Обновление данных — с отменой предыдущего запроса; пока новый набор загружается, фокус остаётся на контроле, которым пользователь взаимодействовал. Вернувшись из деталей, пользователь должен увидеть **тот же фильтр и ту же карточку**.

### 4.3. Карточки

| Назначение | Соотношение сторон | Что показываем |
|---|---|---|
| Тайтл в каталоге | **2:3** | Постер + название; бейдж новинки факультативно |
| Эпизод | **16:9** | Номер, название, длительность, просмотрено/не просмотрено |
| Продолжить просмотр | **16:9** | Изображение, метаданные серии и прогресс |
| Тематическая коллекция | **1:1** или wide | Название коллекции |

Не размещать длинные описания на каждом постере и не добавлять 4–5 бейджей одновременно. Текст не должен закрывать лицо или ключевую часть постера.

## 5. Экран деталей фильма

### 5.1. Сверху вниз

```text
┌──────────────────────────────────────────────────────────────┐
│ backdrop с градиентом, слева читаемый текст                  │
│                                                              │
│ Название фильма                                              │
│ 2026 · 16+ · 2 ч 08 мин · Фантастика                         │
│ Краткое описание (2–4 строки)                                │
│ [▶ Продолжить / Смотреть] [+ Мой список] [Трейлер]           │
├──────────────────────────────────────────────────────────────┤
│ Подробнее / Актёры / Жанры                                   │
│ Похожие фильмы → [постер] [постер] [постер] ...               │
└──────────────────────────────────────────────────────────────┘
```

Первая фокусируемая кнопка — **главное действие просмотра**. Если фильм начат, подпись `Продолжить с 42:15`; действие «Смотреть сначала» — вторичным пунктом.

Не делать трейлер обязательным шагом. Развёрнутые описания и актёров можно отложить до второй версии, но API-модель должна их поддерживать при необходимости.

### 5.2. Ошибочные состояния

- Тайтл доступен, поток недоступен: оставляем страницу деталей и предлагаем «Повторить» или информируем о недоступности.
- Тайтл удалён из каталога: понятный экран без бесконечной загрузки.
- Возрастное ограничение: не нарушать родительские ограничения при открытии прямого deep link.

## 6. Экран деталей сериала — отдельные правила

Не переносить дизайн фильма на сериал без изменений. Здесь ключевое — **выбор сезона и эпизода**.

### 6.1. Структура

```text
[Backdrop / логотип сериала / метаданные]
[▶ Продолжить S02E05] [Мой список] [Трейлер]

Сезоны: [Сезон 1] [Сезон 2 • выбран] [Сезон 3]

Эпизоды сезона:
 [16:9]  1. Название серии         48 мин  ✓ просмотрено
 [16:9]  2. Название серии         50 мин  ✓ просмотрено
 [16:9]  3. Название серии         47 мин  ▶ на 19:26
 [16:9]  4. Название серии         45 мин  ○ не начато

[Похожие сериалы]
```

### 6.2. Логика первичного выбора

**Если сериал не смотрели:** выбран первый доступный сезон, первая доступная серия (учитывать нестандартную нумерацию и спецвыпуски).

**Если смотрели:** выбран сезон, содержащий `nextPlayableEpisode`; главный CTA указывает на эту серию. При входе на страницу необязательно автоматически прокручивать весь экран к этой серии — достаточно корректного главного CTA и указания активного сезона.

**Если сериал досмотрен:** CTA = «Пересмотреть» либо «Смотреть снова»; если появился новый сезон — «Смотреть новую серию».

### 6.3. Селектор сезона

- Для 1–4 сезонов допустимы горизонтальные вкладки.
- Для большого количества сезонов — компактный popup/dropdown с D-pad и обязательным сохранением фокуса после выбора.
- При переключении сезона список серий меняется **без перехода на отдельный экран**.
- Номер сезона не считать равным индексу массива. Могут существовать `Season 0`, specials, неполные сезоны.

### 6.4. Карточка эпизода

- Thumbnail 16:9.
- `№ серии + заголовок`, 1–2 строки синопсиса (по возможности), длительность.
- Прогресс и статус: не начато / в процессе / просмотрено.
- При OK — сразу запуск этого эпизода, без второго экрана подтверждения.
- При длительном OK контекстное меню **не обязательно** для MVP; если вводится, не должно мешать обычному OK.
- Не спойлерить будущие эпизоды: осторожно с synopsis и thumbnail (возможен безопасный fallback).

## 7. Плеер: специальное поведение для фильмов и сериалов

### 7.1. Устройство плеера

**Технология:** Media3 `ExoPlayer`; UI может использовать `PlayerView` в `AndroidView` (проверенная базовая реализация) либо Compose-слой поверх `PlayerSurface`, если нужен полностью кастомный TV-дизайн. Не смешивать два независимых контроллера с конкурирующей обработкой клавиш.

**Первое правило:** важнее надёжная перемотка, стабильность и поддержка форматов, чем визуальные эффекты контролов.

### 7.2. Клавиши

| Кнопка | В режиме просмотра | В открытом меню/диалоге |
|---|---|---|
| OK | Пауза/возобновление | Подтвердить выбранный пункт |
| Left/Right | Перемотка небольшим шагом | Навигация по пунктам |
| Long Left/Right | Длительная перемотка / scrub | Не должна случайно перематывать видео |
| Up/Down | Показать контролы/информацию | Перемещение фокуса |
| Back | Выход из плеера (с фиксацией позиции) | Сначала закрыть меню |
| Play/Pause | Воспроизведение/пауза | По смыслу проигрывателя |

**Не ломать системные правила управления.** Перед обработкой `onKeyEvent` проверить, не решил ли соответствующее действие сам Media3/системный компонент.

### 7.3. Продолжение и сохранение прогресса

Рекомендуемая стратегия:

- Позиция хранится **по `profileId + playableId`**, а не по `titleId` для всего сериала.
- Сохранять при `pause`, `stop`, `onStop`, переходе к другой серии и периодически во время просмотра (например, каждые 10–20 секунд).
- Обновление прогресса делать идемпотентным и асинхронным: локальный кеш → синхронизация с сервером.
- На сервере хранить позицию в миллисекундах, длительность, время обновления и признак `completed`.
- При возобновлении избегать повторного начала за пару секунд до конца: если эпизод завершён — запускаем следующий или предлагаем повтор.
- Позиция может стать невалидной после смены версии потока: ограничивать диапазоном `[0, duration]` и учитывать изменения длительности.

**Критерий «просмотрено»:** предпочтительно использовать размеченный `creditsStartMs`/маркер окончания программы. Если таких данных нет — эвристика на основе процента длительности и оставшихся минут; порог выносится в конфигурацию и тестируется на коротких/длинных эпизодах. Одна только проверка `position >= 90%` недостаточна.

### 7.4. Автоматическое продолжение сериала

После достижения конца эпизода:

1. Получить из каталога **следующий доступный** эпизод.
2. Показать небольшую панель: «Следующая серия», её название и таймер (например, 10 с).
3. `OK` — сразу следующий эпизод; `Back/Cancel` — отказаться от автозапуска.
4. При истечении таймера — запустить, **если автопереход включён в настройках профиля**.
5. Если следующего эпизода нет, не запускать ничего и показать ожидаемое завершение.

Таймер не должен срабатывать во время системного диалога, ошибки DRM, выбора аудиодорожки, смены профиля или когда пользователь явно отменил переход. Не перескакивать через недоступные серии без объяснения.

### 7.5. «Пропустить заставку» / «Пропустить ранее»

Добавлять **только если источник предоставляет точные временные сегменты** (`introStartMs`, `introEndMs`, `recapStartMs`, `recapEndMs`). Без метаданных — не угадывать время для всего каталога.

- Кнопка появляется в обозначенном интервале.
- После нажатия выполняется seek на конец сегмента.
- Фокус не перекрывает системные элементы плеера.
- Не размещать несколько одновременно конкурирующих CTA.

### 7.6. Субтитры, дорожки и качество

- Субтитры: выключены / доступные языки / системные настройки отображения, если поддерживаются.
- Аудиодорожки: язык, при наличии — описание дорожки.
- Качество: **Auto** по умолчанию; ручной выбор возможен только если доступен соответствующий выбор и не конфликтует с адаптивным стримингом.
- Сохранять предпочтения **по профилю** (предпочтительный язык аудио/субтитров).
- Не обещать HDR/Dolby/4K на устройствах, не поддерживающих нужный формат/DRM-профиль.

### 7.7. Жизненный цикл

Когда видео не должно продолжаться в фоне, корректно приостанавливать воспроизведение при уходе приложения с переднего плана. `MediaSessionService` нужен **не всегда** — в основном когда требуется фоновое воспроизведение/внешнее управление. Не добавлять service и foreground notification «на всякий случай».

При переходах по экрану не создавать по новому `ExoPlayer` на каждую recomposition; плеер должен жить в контролируемой области жизненного цикла, освобождаться при завершении сессии.

## 8. Модель контента и история: заранее убрать архитектурные ошибки

### 8.1. Предлагаемые доменные модели (контракт, не готовый production-код)

```kotlin
enum class TitleType { MOVIE, SERIES }

data class TitleSummary(
    val id: String,
    val type: TitleType,
    val name: String,
    val year: Int?,
    val posterUrl: String?,
    val backdropUrl: String?,
    val ageRating: String?,

)

data class Movie(
    val title: TitleSummary,
    val playableId: String,
    val durationMs: Long?
)

data class Series(
    val title: TitleSummary,
    val seasons: List<Season>
)

data class Season(
    val id: String,
    val seriesId: String,
    val number: Int?,  // спецсезоны и разные каталоги
    val name: String,
    val episodes: List<Episode>
)

data class Episode(
    val id: String,
    val seriesId: String,
    val seasonId: String,
    val sequence: Int, // порядок воспроизведения из каталога
    val displayNumber: Int?,
    val name: String,
    val durationMs: Long?,
    val thumbnailUrl: String?,
    val playableId: String,
    val introStartMs: Long? = null,
    val introEndMs: Long? = null,

)

data class PlaybackProgress(
    val profileId: String,
    val playableId: String,
    val positionMs: Long,

```

В production-модели лучше не загружать все `seasons.episodes` в карточке каждого сериала на главной: `TitleSummary` лёгкий, детали сериала и список серий подгружаются отдельно. DTO источника не передавать напрямую в UI — нужен адаптер/маппинг в доменные модели.

### 8.2. Алгоритм определения следующей серии

1. Берём серверный/локально синхронизированный список доступных эпизодов в **предпочтительном порядке сериала**.
2. Если существует незавершённый активный эпизод — продолжаем его.
3. Иначе находим эпизод после последнего завершённого.
4. Если порядок каталога содержит specials и сезон 0 — правило включения спецэпизодов задаётся метаданными, а не арифметикой `season + 1`.
5. Если следующая серия недоступна, показываем статус; не подменяем незаметно на первую серию следующего случайного сезона.
6. При отсутствии истории — первая основная доступная серия.

### 8.3. Несколько профилей

Даже если на старте только один профиль, все персональные данные ключуются по `profileId`:

- история и позиции;
- список «Моё»;
- просмотренные серии;
- предпочтительные дорожки/субтитры;
- профиль детских ограничений (если они предусмотрены).

Детский профиль — **отдельная задача безопасности доступа**, а не просто фильтр карточек. Проверки должны быть в источнике контента/API, не только в Compose UI.

### 9.1. Что сохранять на каждом разделе


Использовать `SavedStateHandle`/`rememberSaveable` для подходящего UI-состояния и ViewModel/repository для долговременного состояния. **Не сохранять** тысячи объектов постеров в SavedState. URL и данные каталога повторно получать из репозитория/кеша.

### 9.2. Сценарии, которые запрещено ломать

- `Главная → 8-й ряд → 12-й постер → Детали → Back` — возврат к 12-му постеру, а не к началу.
- `Сериалы → Детали → Сезон 3 → Серия 6 → Back` — возвращаемся к выбранному сезону и эпизоду.
- `Каталог → Фильтр «Триллер» → Детали → Back` — фильтр и сетка сохранены.
- `Главная → Детали → Плеер → Back → Back` — сначала детали, затем исходный постер.
- `Быстро 20 раз Right` — фокус не теряется при асинхронной загрузке постеров.
- `Ряд удалён из ответа API` — выбрать ближайший допустимый элемент, не падать.

### 9.3. Compose-подход

- `LazyColumn`, `LazyRow`, `LazyVerticalGrid` из **Compose Foundation**.
- `Modifier.focusRestorer()` на подходящих группах, `focusGroup()` для логических групп.
- В устойчивых контейнерах — `key = title.id` / `key = row.id`, отдельное хранение позиции.
- `FocusRequester` — только для **намеренного восстановления**, а не принудительно на каждом обновлении состояния.
- Для конфликтных направлений использовать управляемые focus properties вместо глобального перехвата клавиш.

**Примечание по API (октябрь 2026):** `TvLazyRow`/`TvLazyColumn` из старого TV Foundation устарели и удалены из соответствующих современных TV Lazy API; ориентир — стандартный Foundation + TV Material-компоненты.

## 10. Design tokens: стартовые числа

Проектировать в логических dp с адаптацией под размеры и overscan-safe области, а не фиксировать UI в физических пикселях 1920×1080/3840×2160.

| Токен | Стартовая рекомендация | Комментарий |
|---|---:|---|
| Фон | `#0D0F13` | Почти чёрный |
| Поверхность | `#1C2028` | Меню и контролы |
| Основной текст | `#F4F6FA` | Контрастный |
| Акцент | `#638CF1` | Один акцент, конфигурируемый |
| Безопасный боковой отступ | `48dp` | Проверить overscan и плотность |
| Безопасный верх/низ | `27dp` | Проверить на разных ТВ |
| Вертикальный постер | `124×186dp` | Тип 2:3 |
| Карточка эпизода | `196×110dp` | Тип 16:9 |
| Интервал между карточками | `12–20dp` | Место для scale |
| Интервал между секциями | `24–32dp` | Зависит от текста |
| Основной текст | `16–18sp` | Проверять издалека |
| Заголовок секции | `20–24sp` | Проверять с русскими названиями |
| Hero title | `28–36sp` | Не выходить за safe area |
| Focus scale карточки | `1.05×` | Может быть меньше для тесных сеток |
| Focus outline | `2–3dp` | Контрастный на любом постере |
| Focus animation | `120–180ms` | Без тяжёлой layout-анимации |

**Важно:** focus scale не должен отрезаться clip-границей `LazyRow` и залезать на соседние карточки. Добавить внутренние отступы, проверить z-order и места под тень/outline.

## 11. Сеть, загрузка и производительность

### 11.1. Данные

- Сначала отрисовывать shell, скелетоны фиксированного размера и уже кешированный каталог.
- Изображения: запрашивать вариант подходящего размера, не декодировать backdrop 4K в каждую мини-карточку.
- Нужны `poster`, `backdrop`, `episodeStill`; не строить UI, предполагая, что все три всегда есть.
- На новом фокусе не запрашивать полный backdrop мгновенно; применять debounce или отмену предыдущей загрузки.
- Не допускать запуска одного и того же API-запроса на каждую recomposition.
- Подгрузку следующей страницы делать ближе к концу ряда/сетки; сохранить фокус при append.

### 11.2. Состояния загрузки

Каждый экран предусматривает `loading`, `content`, `empty`, `error`, `refreshing`. Скелетоны не должны принимать D-pad фокус. Ошибка одного ряда на главной не должна прятать остальные.

### 11.3. Медиа

- Одна управляемая сессия основного плеера.
- Поддержка отмены/повторения загрузки потока.
- Политика кеширования сегментов видеопотока — осознанная и ограниченная; не хранить крупные видеофайлы без необходимости.
- Тестировать HLS/DASH, seek, смену дорожек, недоступные сегменты и поведение при смене сети.
- DRM, защищённые потоки, UHD/HDR — только при наличии прав, серверной интеграции и совместимых устройств.

### 11.4. Минимальный стек TV-оболочки

```text
UI:             androidx.tv:tv-material + Compose Foundation
State:          ViewModel + StateFlow
Navigation:     Navigation Compose
DI:             Koin или Hilt (один выбранный)
Network:        Ktor или Retrofit (один выбранный)
Local:          Room + DataStore
Images:         Coil
Playback:       Media3 ExoPlayer + UI-контролы
Perf:           Macrobenchmark / Perfetto / Baseline Profiles
```

Текущая проверенная версия TV Material по странице AndroidX на дату документа: `androidx.tv:tv-material:1.1.0`. Версии Media3/Compose BOM фиксировать отдельно по совместимости при интеграции.

## 13. Подробная матрица UX-тестов

### Приёмка P0 — до любого релиза

- [ ] Весь пользовательский путь работает только D-pad/OK/Back.
- [ ] Первый фокус на каждом экране виден.
- [ ] Фокус не теряется после загрузки изображений/пагинации/обновления каталога.
- [ ] `Главная → Детали → Back` возвращает на исходную карточку и скролл.
- [ ] `Каталог с фильтром → Детали → Back` сохраняет фильтр.
- [ ] `Сериал → Сезон N → Эпизод M → Плеер → Back` возвращает на правильное место.
- [ ] Доступность CTA «Продолжить» для уже начатого фильма и сериала.
- [ ] Прогресс серии не подменяется прогрессом всего сериала.
- [ ] После конца серии корректно определён следующий доступный эпизод.
- [ ] Нет самопроизвольного автозапуска следующей серии при открытом меню или ошибке.
- [ ] При недоступном видео нет бесконечного спиннера — видна диагностируемая ошибка.
- [ ] Переключение аудио/субтитров работает или корректно скрывается при отсутствии альтернатив.
- [ ] Видео не продолжает нежелательно играть после выхода на Home.
- [ ] Управление доступно без мыши и сенсорного экрана.

### Приёмка P1 — качество первой публичной версии

- [ ] Повторный запуск приложения сохраняет историю и позицию.
- [ ] Изображения не размыты на 1080p и не требуют лишней памяти на 4K.
- [ ] Нет заметных остановок UI при быстром удержании D-pad.
- [ ] «Продолжить просмотр» не содержит дубликатов одного сериала.
- [ ] Нет фильмов с пустыми активными кнопками/битым placeholder.
- [ ] Список эпизодов допускает 100+ элементов без полной компоновки всех строк.
- [ ] Длинные русские названия и локализованные описания не ломают макет.
- [ ] Кратковременный разрыв сети и восстановление не сбрасывают навигацию.
- [ ] TalkBack и читаемые подписи действий протестированы.

## 14. Порядок реализации TV-MVP без лишнего усложнения

### Фаза 1 — навигационный MVP

**Реализовать:** дизайн-токены, sidebar, Home, ряды постеров, `TitleDetails`, тестовые данные, Back и восстановление фокуса.

**Критерий готовности:** все P0-сценарии навигации без реального потока видео.

### Фаза 2 — сериал как полноценная сущность

**Реализовать:** модели `Series/Season/Episode`, переключение сезонов, карточки эпизодов, основную кнопку правильной серии, «Моё».

**Критерий готовности:** сериал с 3 сезонами, 30+ эпизодами, неполной историей; правильный выбор следующей серии.

### Фаза 3 — Media3 и прогресс

**Реализовать:** ExoPlayer, HLS/DASH по требованиям сервиса, seek, subtitle/audio selection, сохранение позиции, завершение фильма/серии.

**Критерий готовности:** переживает Back, Home, пересоздание activity, медленную сеть.

### Фаза 4 — качество и TV-интеграция

**Реализовать:** авторизацию/профили при необходимости, системный Watch Next, рекомендации/Deep Links, оптимизации изображений и профилирование.

**Критерий готовности:** подтверждённая стабильность на слабой TV-приставке, мониторинг падений, измеренные показатели запуска и плеера.

### Что оставить после MVP

- Автовоспроизведение трейлеров и motion-background.
- Сложную рекомендательную модель.
- Специальные анимации переходов, 3D/poster effects и масштабные blur.
- Полную систему детских профилей, если продукт допускает отдельный этап (не заявлять детский режим без защиты).
- Офлайн-загрузку видео (для телевизора обычно не первый приоритет).

## 15. Дополнение: системная интеграция Android TV

После появления стабильной истории просмотров стоит интегрировать **Watch Next / Play Next** с домашним экраном Android TV: недосмотренные фильмы, незавершённые серии и следующую серию. Это **не то же самое**, что внутренний ряд «Продолжить просмотр».

При добавлении системных программ следует соблюдать требования Android TV: корректно передавать позицию, длительность, тип элемента и обновлять только затронутые записи. Для сериалов — не публиковать несколько серий одного сериала одновременно, когда достаточно актуальной следующей.

Для запуска из домашнего интерфейса понадобится точный deep link в тайтл или конкретную серию. Профильные ограничения и доступность потока нужно проверять и на входе по deep link.

## 16. Решения, которые нужно зафиксировать перед написанием кода

| Вопрос | Рекомендуемое значение для MVP |
|---|---|
| Источник каталога | Один адаптируемый API, DTO изолированы от UI |
| Авторизация | Если требуется: QR/code login для ТВ вместо длинного пароля на пульте |
| Профили | Один профиль в UI допустим; `profileId` обязателен в данных прогресса |
| Боковое меню | Свёрнутый rail + модальное раскрытие, переход по OK |
| Hero autoplay | Выключен |
| Продолжение просмотра | Один элемент на фильм/сериал, точный `playableId` |
| Выбор сезона | На странице деталей, без отдельной навигации |
| Следующая серия | Через явные отношения в каталоге, не через инкремент номера |
| Skip intro | Только при наличии размеченных таймкодов |
| Фоновое воспроизведение | Выключено; service только по реальной необходимости |
| UI плеера | Сначала базовый стабильный Media3, затем кастомизация |
| Рендер карточек | 2:3 для каталога, 16:9 для эпизодов/продолжения |
| Стратегия работы | Малые вертикальные срезы + тесты фокуса/плеера после каждого |

### Общая оценка

**Самый большой UX-риск — не цветовая палитра, а потеря фокуса/скролла и неправильный выбор следующей серии.** Если эти две области реализованы правильно, приложение уже будет ощущаться значительно надёжнее большинства простых TV-клиентов.

# Часть II. Android Phone / Tablet / Foldable — UX/UI и техническая спецификация

> **Сфера действия:** этот раздел дополняет TV-спецификацию (разделы 1–17), не заменяя её. **Общие:** каталог, доменная логика фильмов/сериалов, профили, авторизация, рекомендации, история, прогресс, сетевой API, ExoPlayer-движок. **Раздельные:** навигационные оболочки, дизайн-компоненты, обработка ввода, отображение каталога/деталей и UI-контролы плеера. Все размеры ниже — проектные стартовые значения, не системные нормативы.

## 18. Принцип: один видеосервис, два способа взаимодействия

Главная ошибка — уменьшить интерфейс Android TV и считать его мобильным. На телефоне пользователи **касаются**, **прокручивают**, **вводят текст**, используют системные жесты, многооконность и часто смотрят контент в дороге. На ТВ пользователь управляет **фокусом с пульта** и смотрит издалека.

| Область | Android TV | Android Phone (compact) | Tablet / Foldable |
|---|---|---|---|
| Главная навигация | Левый NavigationDrawer/rail | Нижняя NavigationBar (4–5 пунктов) | NavigationRail / адаптивная панель |
| Основное действие | D-pad → OK | Tap по карточке или кнопке | Tap, мышь, клавиатура, иногда D-pad |
| Главный экран | Широкий hero + горизонтальные ряды | Компактный hero + горизонтальные ряды | Несколько колонок, более просторный hero |
| Каталог | Постерные ряды/сетки с фокусом | 2 колонки постеров, фильтры-чипы | 3–6 колонок по доступной ширине |
| Экран тайтла | Backdrop + данные слева | Вертикальная страница, CTA возле начала | Two-pane при достаточном пространстве |
| Серии | Горизонтальные карточки или TV-лист | Вертикальный список эпизодов | Сетка/список и панель деталей |
| Выбор сезона | TV-селектор | Кнопка/чип → Bottom Sheet | Tabs/selector/side panel |
| Плеер | Полноэкранно, стрелки/OK | Touch controls, portrait и landscape, PiP | Подстраивается к окну |
| Поиск | Системная экранная клавиатура/голос | Клавиатура IME, подсказки, история | Поиск с гибкой раскладкой |
| Настройки | Минимум действий пультом | Обычные Material 3-экраны | Адаптивные настройки |

**Проектное решение:** сохранить узнаваемую визуальную идентичность и контент между платформами, но не стремиться к 100% совпадению экранов и composable-функций.

## 19. Информационная архитектура на телефоне

### 19.1. Нижняя навигация

Рекомендую **пять элементов**: **Главная**, **Фильмы**, **Сериалы**, **Моё**, **Поиск**. Если нижняя панель визуально перегружена, оставить четыре (**Главная**, **Каталог**, **Моё**, **Поиск**), а «Фильмы/Сериалы» сделать вкладками внутри каталога. Выбирать одну схему и придерживаться её.

Правила:

- `NavigationBar` показывать только на корневых экранах. В `TitleDetails` и полноэкранном `Player` она, как правило, скрыта.
- Вкладка должна сохранять **собственный back stack** и состояние скролла/фильтров; повторное нажатие уже выбранной вкладки можно использовать для возврата наверх **после явного согласования UX**.
- Смена вкладки не должна повторно скачивать весь каталог: использовать repository/cache и длительно живущее состояние.
- Профиль и настройки — через кнопку-аватар в верхней части (не обязательно шестая вкладка).
- Поиск — реальный экран ввода, с автофокусом поля по сознательному пользовательскому переходу, а не при автоматическом восстановлении состояния.

**NavigationBar** по документации Android рассчитан на 3–5 важных направлений на компактных экранах.

### 19.2. Дерево навигации

```text
MobileAppShell
├── MainTabs (по одному стеку на вкладку)
│   ├── Home
│   ├── Movies
│   ├── Series
│   ├── MyList / ContinueWatching / Downloads
│   └── Search
├── TitleDetails(titleId)
│   ├── SeasonsPicker (BottomSheet)
│   └── EpisodeActions (BottomSheet)
├── Player(playableId, sourceRoute)
│   ├── AudioSubtitlesSheet
│   └── QualitySheet
├── ProfileChooser / SignIn / Settings
└── Downloads (если функция включена)
```

- Системный жест **Back / predictive back** закрывает сверху вниз: sheet → полноэкранный дочерний экран → вкладку/корень; не подменять стандартные жесты самодельным swipe-навигационным механизмом.
- Deep link `title/{id}` и `watch/{playableId}` должен открываться корректно из уведомлений, ссылок и Cast flow, с учётом авторизации и прав на контент.
- Переключение профиля инвалидирует персональные данные и доступность контента; нельзя показывать чужую историю из памяти предыдущего профиля.
- Для нового проекта выбрать **одну** навигационную библиотеку; Navigation Compose — консервативный вариант, Navigation 3 — подход при готовности явно управлять стеком. Не реализовывать два роутера одновременно.

## 20. Главная страница мобильной версии

### 20.1. Порядок блоков

1. Компактная верхняя панель: логотип/текущий профиль, поиск (если нет вкладки), Cast (если поддерживается).
2. Featured: **один** крупный тайтл, ограниченная высота; без принудительного autoplay-видео.
3. «Продолжить просмотр» — максимально высоко, если есть история.
4. «Мой список» — если данные существуют; не дублировать пустые секции.
5. Персональные рекомендации.
6. Новинки/популярное/подборки по жанру.

**Оптимизация:** после возврата из деталей или плеера лента восстанавливается на том же тайтле/позиции. При смене вкладки состояние может храниться отдельно для каждой вкладки.

### 20.2. Карточки

| Тип | Где | Данные | Поведение |
|---|---|---|---|
| `PosterCard` 2:3 | Каталог и жанры | Постер, название (при необходимости) | Tap → детали |
| `LandscapeCard` 16:9 | Рекомендации/подборки | Превью, заголовок | Tap → детали |
| `ContinueCard` 16:9 | История | Превью, тонкая полоса прогресса, серия | Tap → продолжить или открыть детали согласно явно обозначенному действию |
| `EpisodeRow` 16:9 слева | Экран сериала | Thumbnail, номер, название, длительность, прогресс | Tap → воспроизвести; контекстное меню — отдельно |
| `FeaturedHero` | Верх главной | Backdrop, название, 1–2 CTA | Tap по «Смотреть»/«Подробнее» |

Рекомендуемая геометрия **для мобильного прототипа**:

- Горизонтальный padding контейнера — 16dp (можно 20–24dp на просторных окнах).
- Зазоры в каталоге — 8–12dp.
- Секция по вертикали — 20–28dp.
- Компактный постер: 2 колонки на телефонной ширине в каталоге; на ширине около 360dp с отступами 16dp и gap 12dp элемент имеет ~158dp ширины.
- Минимальная активная сенсорная зона — **48×48dp**, даже для маленькой иконки; фактическая картинка внутри может быть меньше.
- Высоту Featured сделать динамической и ограниченной: не занимать весь первый экран, если «Продолжить просмотр» важнее рекламы премьеры.
- Текст названия карточки — 1–2 строки, с `maxLines`/ellipsis; флаги формата и жанров не накладывать поверх постера без необходимости.

### 20.3. Заглушки, ошибки и движения

- Сначала отрисовать кешированные секции или skeleton фиксированной геометрии; `pull-to-refresh` — на главной/каталоге, если он действительно обновляет данные.
- Ошибка одного ряда не должна уничтожать остальные.
- Поиск и фильтры с `debounce` и отменой устаревшего запроса.
- Не создавать тяжелую параллакс-анимацию или видео в каждой карточке.
- Изображения запрашивать размера под фактический контейнер и плотность пикселей; избегать одновременного декодирования десятков полноразмерных backdrops.

## 21. Мобильный экран фильма и сериала

### 21.1. Фильм

Порядок сверху вниз:

1. Верхняя панель: системный Back, действия «Избранное/Поделиться» по необходимости.
2. Backdrop (16:9 либо широкая обрезка), с контрастным градиентом.
3. Название, год, длительность, возрастной рейтинг, 1–2 жанра.
4. Главный CTA **«Смотреть»/«Продолжить»**, хорошо заметный на компактной высоте экрана.
5. `Добавить в Моё` и дополнительные действия — вторичные.
6. Краткое описание с «Развернуть» вместо огромной стены текста.
7. Состав, рекомендации, подобное кино (по наличию данных).

### 21.2. Сериал

Порядок: CTA продолжения → описание → **выбор сезона** → список серий → похожие сериалы.

- Для первой серии: «Смотреть S01E01»; если последняя позиция незавершена — «Продолжить S02E06»; если серия закончена — следующая доступная.
- Выбор сезона на compact phone: **ModalBottomSheet** с ясным списком сезонов. На large width допустимы tabs/side rail.
- После выбора сезона сохранить `selectedSeasonId` при скролле, Back и повороте экрана.
- В каждой строке эпизода показывать thumbnail, `SxxExx`, длительность, название и прогресс; длинные описания — по раскрытию или отдельному нажатию.
- Не запускать новую серию от простого пролистывания списка: воспроизведение начинается только по явному действию пользователя (кроме разрешённого автоперехода в конце серии).

### 21.3. Мобильный контекстный UX

Long press по постеру **не обязателен**: действие «В мой список» должно быть доступно и обычным нажатием на видимую кнопку или в деталях. Если long press поддерживается, визуально подсказать его назначение, не делать единственным способом доступа к функции.

## 22. Поиск, фильтры и «Моё» на телефоне

### Поиск

- Полноценная строка ввода с IME, очисткой, понятными пустыми состояниями и подсказками.
- Подборки «Недавние запросы» и «Популярное» показывать до ввода.
- При вводе использовать отменяемый запрос после `debounce` (стартовое значение 250–400мс) и отображать `loading` без мерцания результата.
- Поиск по названию, альтернативным названиям, жанру; актёрам — только если каталог/API поддерживает метаданные.
- Сохранять пользовательский запрос и результаты при возврате из деталей.

### Фильтры

- `FilterChip` по жанру/типу/году, сортировка отдельной кнопкой или Bottom Sheet.
- Активные фильтры всегда видимы; «Сбросить» доступно после выбора.
- Сетку делать `LazyVerticalGrid`, item keys — стабильный `titleId`.

### «Моё»

- Вкладки/группы: **Продолжить**, **Мой список**, **Скачанное** (если enabled), **История** (опционально).
- «Продолжить» содержит **одну агрегированную запись на сериал**, привязанную к конкретному `playableId` последней незавершённой серии.
- Не путать «Добавлено в список» с фактом просмотра или завершения эпизода.
- Удаление из «Продолжить» и сброс истории должны быть отдельными операциями; подтверждение только для потенциально необратимого действия.

## 23. Планшеты, складные устройства, альбомная ориентация

Не проектировать по булевому `isTablet`. Использовать **актуальный размер окна** (`WindowSizeClass`) и при необходимости высоту/положение складки (`WindowManager`).

| Доступная ширина окна | Базовое поведение |
|---|---|
| `< 600dp` compact | Нижние вкладки, одна основная колонка, компактный hero |
| `600–839dp` medium | NavigationRail по обстоятельствам, 2–4 постера в каталоге, больше воздуха |
| `840–1199dp` expanded | Rail и полноценная сетка, при достаточной высоте возможен list-detail |
| `1200dp+` large | Подбор плотности сетки и max content width, без чрезмерно растянутых карточек |

Это **окна**, а не диагонали устройств. На планшете в режиме разделённого экрана может быть compact width; телефон в landscape может одновременно иметь medium width и compact height. Не применять двухпанельный layout только на основании ширины, если высота слишком маленькая.

**Android 16 (targetSdk 36) и большие дисплеи:** ограничения ориентации/отношения сторон/изменяемости окна могут игнорироваться системой для устройств с `smallestWidth >= 600dp`. Не фиксировать portrait для всего приложения. Плеер должен менять компоновку при повороте, разворачивании и split-screen без потери позиции. Проверьте актуальные правила Google Play перед релизом.

### Применение к каталогу

- Phone portrait: `LazyVerticalGrid(GridCells.Fixed(2))` или ширина карточки с адаптивным `GridCells.Adaptive` с нижним пределом 140–160dp.
- Tablet: предпочтительнее `GridCells.Adaptive(minSize = 160.dp)` и ограничения на максимальную ширину контентной колонки.
- TitleDetails expanded: изображение и основная информация в двух колонках **при достаточной высоте**, ниже — список эпизодов.
- При наличии складки/hinge не помещать активные controls прямо на пересечении экранов.

## 24. Плеер на телефоне: отдельная оболочка Media3

### 24.1. Основная модель

**Один воспроизводящий движок** Media3/ExoPlayer с единым API команд (`play`, `pause`, `seekTo`, `selectTrack`, `prepare`, `release`) и **разными контролами**:

- TV: OK/Left/Right/Back и фокус TV Material.
- Phone: tap/swipe, кнопки крупными сенсорными зонами, `Slider`/TimeBar, выбор дорожек и субтитров через понятное меню.
- Tablet: controls укладываются в доступную площадь, не обязаны растягиваться по всей ширине.

Использовать `PlayerView` через `AndroidView` как простой стабильный путь либо Media3 Compose `PlayerSurface` и готовые компоненты `media3-ui-compose[-material3]` с осознанной кастомизацией. **Контролы TV и mobile не вкладывать друг в друга**. При Compose UI избегать двух независимых time-bar, соревнующихся за seek.

### 24.2. Портретный режим

Два разумных UX-варианта:

1. **Embedded player** 16:9 наверху, ниже — название, выбор серии и похожий контент. Лучше для мобильного потребления и быстрого возврата к каталогу.
2. **Fullscreen player** по пользовательскому действию (иконка разворачивания), системные бары скрываются только в полноэкранном режиме.

Рекомендация: запускать в portrait со встроенным плеером, если концепция допускает страницу просмотра; по кнопке Fullscreen переводить в landscape, **где разрешено**, и плавно скрывать вторичный UI. При вращении устройства не дублировать инстанс плеера и не повторять загрузку stream URL без причины.

### 24.3. Контролы и жесты

| Действие | Результат |
|---|---|
| Tap по видео | Показать/скрыть controls |
| Центральная кнопка | Play/Pause |
| Кнопки ±10с | Точный seek (порог настраиваемый) |
| Перетягивание TimeBar | Scrubbing + time preview, если доступно |
| Двойной tap по сторонам | ±10с, **опционально**, с явной обучаемой подсказкой |
| Swipe для яркости/громкости | **Опционально**, не MVP; не мешать системным жестам |
| Fullscreen | Переход между встроенным и полноэкранным режимом |
| Аудио/субтитры | Bottom Sheet или отдельное меню |
| Свернуть / Back | Возврат к каталогу с сохранением позиции, если PiP/фоновое воспроизведение не активно |

- Не ставить невидимую огромную область, которая перехватывает системный edge-swipe Back.
- Tap для показа контролов **не должен автоматически ставить паузу**, иначе сложно управлять таймлайном.
- При блокировке ориентации/системных ограничениях не форсировать landscape насильно; обеспечить рабочий fullscreen и в portrait.
- Субтитры не должны перекрываться TimeBar; при открытых контролах обеспечить читаемость.

### 24.4. Поведение при сворачивании

Определить **явную политику продукта**, а не смешивать сценарии:

- **MVP:** при уходе с экрана/в фон без PiP — сохранить позицию и приостановить видео.
- **PiP (после MVP или отдельный P1):** если пользователь смотрит видео и активировал/разрешил PiP, перейти в Picture-in-Picture при подходящем сценарии; поддержать управление из системного окна и возврат в Activity. На Android 12+ возможно `setAutoEnterEnabled(true)`, но **только когда PiP уместен**.
- **Background playback:** если намеренно нужен звук с погашенным экраном/после Home, использовать `MediaSession` + `MediaSessionService` и корректное foreground service/уведомление. Не запускать это без продуктового требования.
- **Audio focus и headset events:** учитывать потерю фокуса, телефонные вызовы, подключение гарнитуры, внешние команды MediaSession.

### 24.5. Следующая серия

Единая доменная политика с TV: следующий `playableId`, честная обработка отсутствующей серии, skip intro строго по метаданным. На мобильном устройстве UI предложения о следующей серии располагается **поверх плеера у конца эпизода**, но не закрывает субтитры/системныеcontrols; автозапуск доступен только при включённом preference.

## 25. Mobile-only: скачивание, Cast, PiP

### 25.1. Офлайн-загрузки

Для стримингового приложения это полезная функция, но **существенно отдельный проект**. Не добавлять в MVP, пока не стабилизированы авторизация и воспроизведение.

Требования, если включать:

- Media3 `DownloadService` + `DownloadManager` + `DownloadIndex`; ограничения «только по Wi-Fi», места на диске и параллелизма.
- Статусы `queued/downloading/paused/completed/failed/expired`, отмена и повтор.
- Поддержка только разрешённых типом контента потоков, шифрование/DRM/offline licence при наличии соответствующих прав и возможностей источника.
- Срок действия скачанного контента и понятный сценарий обновления лицензии; удаление по действию пользователя/истечению политики.
- Индикатор объёма в МБ/ГБ и выбор качества заранее, без ложных обещаний доступного места.
- Скачанные данные и ключи защищены, не экспонировать приватный путь в общедоступное хранилище.

### 25.2. Cast

**Google Cast — отдельная технология, а не автоматическое следствие наличия Android TV в сети.** Если нужен «с телефона на телевизор», проверить совместимость receiver, кодеков/DRM и поддержку Cast в стеке.

- Для соответствующего окружения использовать `media3-cast`/`CastPlayer`; Android-телефон работает как sender, compatible receiver — как исполнитель воспроизведения.
- Состояние seek/play/pause и прогресс отображаются синхронно; источник истины — активный remote player.
- Описать переход local → remote → local с переносом позиции, выбранного профиля и access policy.
- Cast не заменяет установку автономного TV-приложения: это **два отдельных способа просмотра**.

### 25.3. Picture-in-Picture

- Включать в манифесте только для экрана/Activity, поддерживающего PiP; хранить разрешённость по текущему воспроизведению.
- Проверять `onPictureInPictureModeChanged` и менять плотность UI на минимальный video-only.
- Не запускать PiP из экрана деталей, поиска или при неактивном видео.
- Настраивать aspect ratio осторожно (у системы есть допустимые границы), тестировать повороты и возврат из PiP.

## 26. Единая архитектура проекта: рекомендованный вариант

### 26.1. Схема

```text
Android monorepo (один репозиторий, одна система моделей)
├── app-mobile/              // Android application: phone/tablet/foldable
│   ├── MobileActivity
│   ├── navigation/           // Material3 bottom bar / adaptive rail
│   ├── theme/
│   └── feature-ui/          // Mobile экраны и mobile player controls
├── app-tv/                  // Android application: Android TV / Google TV
│   ├── TvActivity
│   ├── navigation/           // TvMaterial drawer + D-pad/focus
│   ├── theme/
│   └── feature-ui/          // TV экраны и TV player controls
├── core-model/             // Title, Series, Season, Episode, Profile, PlaybackProgress
├── core-domain/            // use cases, next-episode, policies, contracts
├── core-data/              // repository implementations, mappers
├── core-network/           // Ktor/Retrofit, auth, stream URL resolver
├── core-database/          // Room, DataStore, cache/invalidation
├── core-playback/          // Media3 controller, queue, progress, track prefs
├── core-ui/                // только platform-neutral Compose UI (без MaterialTheme)
│   └── primitives/          // изображение, text format, loading models (по необходимости)
└── test-fixtures/          // каталог, история, fake API, сценарии
```

**Рекомендую отдельные `app-tv` и `app-mobile` с общими модулями**. Это уменьшает смешивание зависимостей (`androidx.tv.material3` против `androidx.compose.material3`), различает manifests/launcher и упрощает тестирование. Альтернатива — один `app` с разделением source sets / runtime device mode; это возможно, но сложнее предотвращать утечки UI-зависимостей и случайный выбор неправильной темы.

Если команда маленькая, физически достаточно: `app-tv`, `app-mobile`, `core`, `feature-shared` — дальнейшее дробление делать по реальным границам зависимости, не ради «чистой архитектуры».

### 26.2. Что действительно переиспользовать

| Модуль | Общий? | Комментарий |
|---|---|---|
| DTO/API/catalog repository | Да | Одинаковый сервер каталога |
| Title/Series/Episode модели | Да | Независимы от form factor |
| Authentication/profile repository | Да | TV login UX отличается, данные едины |
| `NextEpisodeResolver` | Да | Одинаковая бизнес-логика |
| `ContinueWatching`/history sync | Да | Одинаковый контракт и серверный профиль |
| Player engine/queue | Да | Media3 общий, lifecycle policy специфична |
| Feature ViewModel/use cases | Частично | Общие данные/UDF; иногда разный presentation state |
| Design tokens | Частично | Палитра/brand общие; размеры/типографика разные |
| Poster image rendering | Частично | Общая загрузка данных; разная карточка/фокус/нажатия |
| TV focus manager | Нет | Только TV |
| Mobile BottomBar/BottomSheet | Нет | Только mobile |
| Player controls | Нет | Кнопки и input различаются |

Не помещать импорты `androidx.tv.material3.*` в общую feature ViewModel или доменную модель. Не создавать `when (isTv)` внутри **каждой** карточки — лучше отдельные компоненты `TvPosterCard`/`MobilePosterCard` с общим контрактом UI.

### 26.3. Поток данных

```text
UI intent (TV OK / Mobile tap)
     ↓
Feature ViewModel → UseCase → Repository
                         ├── Local Room cache / DataStore
                         ├── Remote API / auth
                         └── Media3 playback coordinator
     ↓
StateFlow<FeatureUiState> → TV Composable или Mobile Composable
```

`UiState` описывает **состояние продукта**, а не пиксели/фокус конкретной платформы. UI shell хранит собственное восстановление focus/scroll/selection. UI events (нажатия, поиск, открытие тайтла) должны быть идемпотентны там, где возможно.

### 26.4. Важные технические границы

- `playableId` — логическая идентичность контента, **не URL потока**. Подписанный `streamUrl` короткоживущий, запрашивается перед проигрыванием и при 401/403 обновляется разрешённым способом; не логировать токены.
- DTO/сериализация источника — только `core-network`; экран не знает формат внешнего API.
- Сервер хранит профильную историю как source of truth; локально сохранять очередь несинхронизированных обновлений, обрабатывать конфликты между TV и phone.
- Обновление локального кеша/данных не должно уничтожать position/scroll.
- `Media3 Player` живёт в сервисе/контроллере согласно выбранному режиму, а не создаётся при каждом `@Composable` вызове.

## 27. Compose: конкретные схемы реализации

### 27.1. Разделение тем

```text
app-tv:      TvMaterialTheme { TvApp() }
app-mobile:  MaterialTheme   { MobileApp() }
core:        без зависимости от двух реализаций MaterialTheme
```

Не помещать две темы вокруг одного дерева, не смешивать mobile Material `Button` с TV Material компонентами внутри одного экрана. Это снижает непредсказуемые эффекты фокуса, размеров и цветов.

### 27.2. Адаптивная навигация Material 3 (пример составления)

Ниже **иллюстративный фрагмент**; `onSelectDestination`, `activeDestination` и `content` предоставляются владельцем навигационного стека, а `Destination` и иконки определяются проектом.

```kotlin
@Composable
fun MobileShell(
    activeDestination: Destination,
    onSelectDestination: (Destination) -> Unit,
    content: @Composable () -> Unit
) {
    NavigationSuiteScaffold(
        navigationSuiteItems = {
            Destination.entries.forEach { destination ->
                item(
                    selected = destination == activeDestination,
                    onClick = { onSelectDestination(destination) },
                    icon = {
                        Icon(
                            imageVector = destination.icon,
                            contentDescription = destination.label
                        )
                    },
                    label = { Text(destination.label) }
                )
            }
        }
    ) {
        content()
    }
}
```

Используется `androidx.compose.material3.adaptive.navigationsuite.NavigationSuiteScaffold` (добавить зависимость `material3-adaptive-navigation-suite` по совместимой с Compose версии). Для полноэкранного плеера и экранов деталей лучше оборачивать оболочкой **только корневые маршруты**.

### 27.3. Сетка постеров (пример составления)

```kotlin
@Composable
fun MobilePosterGrid(
    titles: List<TitleSummary>,
    onTitleClick: (String) -> Unit,
    modifier: Modifier = Modifier
) {
    LazyVerticalGrid(
        columns = GridCells.Adaptive(minSize = 150.dp),
        modifier = modifier.fillMaxSize(),
        contentPadding = PaddingValues(16.dp),
        horizontalArrangement = Arrangement.spacedBy(12.dp),
        verticalArrangement = Arrangement.spacedBy(20.dp)
    ) {
        items(items = titles, key = { it.id }) { title ->
            MobilePosterCard(
                title = title,
                modifier = Modifier.fillMaxWidth(),
                onClick = { onTitleClick(title.id) }
            )
        }
    }
}
```

`MobilePosterCard` — мобильная реализация с корректной touch target/semantics, `AsyncImage` с 2:3 и fallback. Пример не претендует на готовую компиляцию без импортов/компонентов проекта. Для узкого телефона проверить итоговое число колонок: adaptive min-size может дать не ровно две.

### 27.4. Edge-to-edge + insets

На Android 15+ при `targetSdk >= 35` edge-to-edge применяется системой. В `Activity.onCreate()` можно вызвать `enableEdgeToEdge()` для согласованного поведения на более ранних версиях; в Compose учитывать `WindowInsets`, `Scaffold` content padding и IME. **Не применять systemBarsPadding два раза** на одном пути контейнеров.

```kotlin
class MobileActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        enableEdgeToEdge()
        setContent { MobileApp() }
    }
}
```

В fullscreen плеере управлять системными барами отдельно. На главном экране кнопки нижней навигации не должны быть накрыты жестовой системной полосой; в поиске `imePadding`/resize должны предотвращать перекрытие выдачи клавиатурой.

### 27.5. ViewModel: общие состояния, разное отображение

```kotlin
data class TitleDetailsUiState(
    val title: TitleSummary? = null,
    val isLoading: Boolean = false,
    val errorMessage: String? = null,
    val availableSeasons: List<Season> = emptyList(),
    val selectedSeasonId: String? = null,
    val recommendedPlayableId: String? = null,
    val isInMyList: Boolean = false

interface TitleDetailsActions {
    fun selectSeason(seasonId: String)

```

UI на телефоне может представить сезон в bottom sheet, TV — в focusable tabs. Но оба вызывают `selectSeason` и используют одно правило определения следующего `playableId`.

## 28. Авторизация, профили и синхронизация TV ↔ phone

**Пользователь воспринимает оба устройства как один сервис.** Поэтому единые данные важнее, чем визуальное совпадение.

### 28.1. Авторизация

- На телефоне стандартная форма/OAuth provider (при его наличии) с системным браузером; не хранить пароль в открытом виде.
- На TV предпочтителен device-code/QR login: показ кода на телевизоре, подтверждение на телефоне. Подтверждение токена с сервера — обязательное, а не только локальная отметка UI.
- Токены хранить по платформенным практикам безопасного хранения; не записывать bearer токены, DRM license и персональные данные в логи.
- Logout очищает секреты и персональные кеши данного аккаунта, предотвращая утечку данных в профили другого человека.

### 28.2. Синхронизация прогресса

**Инвариант:** `accountId + profileId + playableId` определяют историю, и у обоих клиентов единый серверный контракт.

Пример:

```json
{
  "accountId": "account-A",
  "profileId": "profile-1",
  "playableId": "episode-s02e06",
  "positionMs": 1245000,
  "durationMs": 2580000,
  "completed": false,
  "updatedAtEpochMs": 1792497600000,
  "sessionId": "device-session-123",
  "revision": 17
}
```

`updatedAtEpochMs` в примере иллюстративен. Важные правила:

1. Прогресс записывается локально немедленно и асинхронно синхронизируется с сервером.
2. Запись **pause/stop/end** важнее периодической; при offline/network failure хранить очередь на повторную отправку.
3. Конфликты нельзя решать только правилом `max(position)`: перемотка назад — намеренное действие, завершение серии — отдельный статус.
4. Использовать серверную ревизию/сессию/идемпотентность событий и детерминированную политику разрешения конфликта; часы устройства не считать абсолютной истиной.
5. При старте на другом устройстве проверять последний синхронизированный прогресс. Если локальная несинхронизированная версия новее по смыслу, предлагать восстановление без неожиданных прыжков.
6. Завершённая серия должна корректно превращаться в «следующую», а не возвращаться последней незавершённой из-за очередности ответов.

### 28.3. Синхронизация «Моего списка»

Для операции добавления/удаления предусмотреть дедупликацию и обратимую ошибку оптимистичного UI. При одновременных действиях с TV и phone серверное состояние должно стать согласованным без неконтролируемого «мигания» карточек.

## 29. Сборка, зависимости, AndroidManifest и выпуск

### 29.1. Отдельные application-модули — практичный default

```text
:app-mobile  → applicationId: com.example.stream
:app-tv      → applicationId: com.example.stream.tv (пока отдельные продукты)
                  ↘ общий backend/account/profile
```

Это **пример именования**, а не готовые идентификаторы. Можно выбрать общую продуктовую схему и публикацию в Google Play с единым package name и дифференцированными сборками, но тогда нужна осознанная стратегия delivery/манифестов и тестов. **Не публиковать два APK с несовместимым package ID как будто это автоматически одно приложение.**

### 29.2. TV-особенности манифеста

Для TV-приложения нужны `LEANBACK_LAUNCHER`, баннер/иконка и отсутствие требования touchscreen. Если **один APK предназначен и для TV, и для телефона**, `android.software.leanback` и `android.hardware.touchscreen` должны иметь `required="false"`; манифест и launcher category должны соответствовать поддерживаемым форм-факторам.

```xml
<!-- Фрагмент manifest для объединённой поставки (не полный manifest) -->
<uses-feature android:name="android.software.leanback"
    android:required="false" />
<uses-feature android:name="android.hardware.touchscreen"
    android:required="false" />

<!-- Для TV launch activity: android.intent.category.LEANBACK_LAUNCHER -->
<!-- Для Phone launch activity: android.intent.category.LAUNCHER -->
```

Если приложения **раздельные**, `app-tv` оформляется как TV-продукт, `app-mobile` как mobile. Не тянуть телевизионный лаунчер и баннеры в мобильный модуль без необходимости.

### 29.3. Зависимости

```text
shared:
  Kotlin, Coroutines/Flow, Room, DataStore, Ktor/Retrofit,
  Media3 ExoPlayer/Session, domain/data modules

app-mobile:
  Compose BOM + androidx.compose.material3:material3
  androidx.compose.material3:material3-adaptive
  androidx.compose.material3:material3-adaptive-navigation-suite
  androidx.activity:activity-compose, navigation (выбранная одна система)
  Media3 mobile UI, Coil Compose

app-tv:
  Compose BOM + androidx.tv:tv-material
  Compose Foundation / UI / runtime, navigation (одна система)
  Media3 TV UI, Coil Compose
```

Зафиксировать версии в `libs.versions.toml`, сверять Google Maven/релизные заметки, не задавать одинаковые версии библиотек из разных release train наугад. `Media3` модули держать одной совместимой версии. Для TV оставить только нужные mobile UI библиотеки там, где это необходимо Media3, и не вводить вторую `MaterialTheme` на экран.

| Этап | Изменение | Критерий приёмки |
|---|---|---|
| 0 | Зафиксировать contracts, сценарии и каталог test fixtures | Модели фильма/сериала едины |
| 1 | Вынести из TV-кода общие domain/data/repository | Unit tests без запуска Android UI |
| 2 | Добавить `app-mobile` + Material3 theme + nav shell | Телефон запускается, 4–5 вкладок, Back работает |
| 3 | Главная/каталог/постеры/поиск на мобильном | Стабильный state и scroll |
| 4 | Детали фильма/сериала/сезоны/эпизоды | Правильный `playableId` для CTA |
| 5 | Мобильный Media3 player/seek/subtitle/audio | Корректный lifecycle и возврат |
| 6 | Прогресс, аккаунты/профили и cross-device sync | TV↔phone handoff проходит |
| 7 | Адаптивный UI планшета и foldables | Работают resize/rotation/multi-window |
| 8 | Производительность, accessibility, crash/error states | Матрица P0 зелёная |
| 9 | Cast/PiP/offline — по одному, если есть бизнес-требование | Каждый feature имеет независимые тесты |

**Не переписывать TV-интерфейс ради общей мобильной поддержки.** Сначала выделить бизнес-логику с тестами, затем построить мобильный UI поверх существующих API. Каждая стадия должна давать работающее приложение без регрессий на телевизоре.
