# S-005 — что и как измеряем

Документ фиксирует протокол измерений для плана v3 §3.3: метрика → инструмент → где он реально
есть в проекте → что считается провалом. Числа в конце — первый срез, они не являются SLA.

## 1. Доступный инструментарий (проверено)

| Метрика | Инструмент в этом репозитории | Статус |
|---|---|---|
| Длительность кадров P50/P90/P95/P99, jank, missed vsync, slow UI | `dumpsys gfxinfo <pkg>` через `scripts/perf_metrics.py` | работает, снимается за окно сценария |
| Per-frame trace главного потока (sched + gfx + view + input + wm) | Perfetto через `scripts/perf_metrics.py --perfetto` | работает: трасса 14.8 МБ за 15 с, конфиг подаётся через stdin (SELinux не даёт читать `/data/local/tmp`) |
| Холодный/тёплый старт | `am start -W` (TotalTime/WaitTime), `scripts/perf_smoke.py` | работает |
| Память после циклов | `dumpsys meminfo` (TOTAL PSS), до/после в том же JSON | работает |
| Условия запуска | модель, sdk, emulator-флаг, экран, density, температура/заряд батареи, Wi-Fi/mobile | пишется в каждый отчёт автоматически |
| Воспроизводимые данные | `scripts/perf_fixtures.py` (100/1000/10000, битые постеры) | работает (эмулятор + root) |
| Сценарии | `scripts/perf_smoke.py`, instrumentation-тесты, `build/manual/scenarios_generic.py` | работает |
| **FrameOverrun / FrameTimingMetric** | Macrobenchmark `FrameTimingMetric` | **недоступно**: нет модуля `:macrobenchmark`, тестовое устройство API 30 (< 31) |
| Recomposition | Layout Inspector / Compose compiler reports | только в IDE, скриптом не снимается |
| Image decode/cache churn | Coil/Glide events + profiler | только вручную в profiler |
| Network request IDs | Network Inspector | только в IDE |

## 2. Пороги (проектные, не официальные Android SLA)

Берутся из плана §3.3 и применяются к **одному и тому же** устройству/сборке:

- P95 длительности кадра на прокрутке — не хуже baseline; цель — отсутствие систематических
  выбросов P99, каждый выброс разбирается по Perfetto отдельно.
- Тап → видимая реакция ≤ 100 мс (дальнейшая подгрузка — асинхронно).
- Нет блокировки main thread > 50 мс на обычных переходах (проверяется трассой).
- После 10 циклов навигации и открытия деталей PSS не растёт систематически (разброс прогонов
  учитывается).
- `frameOverrunMs` ≤ 0 для P95 — **цель недостижима к измерению в текущей среде**, пока нет
  API 31+ и модуля macrobenchmark; отмечено как долг, а не как выполненный пункт.

Абсолютный FPS эмулятора как критерий релиза **не используется**.

## 3. Протокол прогона

```sh
# 1. Одинаковые данные: эмулятор + фикстуры, либо реальный каталог (фиксируется в отчёте).
python scripts/perf_fixtures.py load --serial emulator-5556 --size 1000
# 2. Приложение в нужном экране, экран включён.
# 3. Снять окно: gfxinfo + Perfetto + память + условия.
python scripts/perf_metrics.py --serial emulator-5556 --seconds 15 --perfetto \
    --out build/perf/cNN/metrics-scroll.json
```

Обязательные условия сопоставимости (пишутся в JSON автоматически): устройство/эмулятор и его
образ, API, разрешение и density, заряд/температура батареи, включённые сети, состояние экрана,
сборка (debug/benchmark), набор данных, длительность сценария и число жестов. Сравнивать можно
только прогоны, где эти поля совпадают; иначе разница не интерпретируется.

`--perfetto` сам ждёт завершения трассировки по `duration_ms` и вытягивает `.pftrace` в
`build/perf/<cycle>/traces/`. Трассы и JSON — игнорируемые артефакты `build/`, в Git не идут.

## 4. Первый срез (эмулятор Pixel_5 API 30, debug, реальный каталог)

Сценарий: прокрутка «Фильмов» 15 с, одинаковые условия, два прогона.

| Прогон | Кадров | Janky | P50 | P90 | P95 | P99 | PSS до/после |
|---|---:|---:|---:|---:|---:|---:|---|
| с Perfetto | 843 | 608 | 18 | 27 | 31 | 57 | 184 444 → 192 718 КБ |
| без Perfetto | 863 | 637 | 18 | 29 | 29 | 61 | (не снималось) |

Артефакты: `build/perf/c27/metrics-scroll.json`, `metrics-scroll-run2.json`,
`build/perf/c27/traces/c005.pftrace` (14 801 110 байт).

Как это читать: два прогона в одинаковых условиях дают близкие P50/P95 (18/31 и 18/29 мс), то
есть протокол воспроизводим. При этом «janky» 70 % — нормальная картина для debug-сборки на
эмуляторе: порог 16.67 мс здесь не выдерживается почти всегда, поэтому **по этим числам нельзя
делать вывод о проблемах UI**. Разница PSS +8 МБ за один прогон без цикла навигации также
не показатель утечки: heap прогревается (кэш постеров, JIT).

## 5. Что осталось непроверенным

- `frameOverrunMs`/`FrameTimingMetric` не снимаются (нет API 31+ и модуля macrobenchmark).
- Recomposition, image-cache churn и сетевые повторы — только вручную через Android Studio.
- Прогоны на release/benchmark-сборке и на физическом устройстве ещё не сделаны (по решению
  оператора плавность на телефоне проверяется отдельно).
