# PERF_REPORT — S-007 (PERF-02)

c-29, revision 15. Сборка: debug, `com.arny.mobilecinema.perfdebug` с фикстурами 1000 карточек.
Устройство: Pixel_5 API 30 (эмулятор). Сценарий: 15 с одинаковых свайпов по сетке «Фильмы»,
`scripts/perf_metrics.py`. Телефон по решению оператора не использовался.

## 2. Что изменено

- `HomeFragment`, `MobileCatalogFragment`: `collectAsState()` → `collectAsStateWithLifecycle()`
  (4 места). Подключена `androidx.lifecycle:lifecycle-runtime-compose` версии 2.7.0 — та же
  версия, что и уже используемый `lifecycle-runtime-ktx`; TV-экраны не затронуты.
- Смысл: коллекция состояния прекращается, когда экран не STARTED, и возобновляется при
  возврате; раньше поток собирался и в фоне.

## 3.1. Трасса главного потока (atrace, тот же сценарий)

Снята текстовая atrace-трасса (`gfx`, `view`, `sched`, буфер 20 МБ) на прокрутке 15 с:
`build/perf/c30/c30.trace` (332 077 строк), разбор — `build/perf/c30/atrace-summary.json`,
скрипт — `build/perf/c30_atrace.py`.

| Метрика главного потока | Значение |
|---|---:|
| `Choreographer#doFrame` слайсов | 918 |
| медиана | 5.23 мс |
| P95 | 9.81 мс |
| максимум | 41.48 мс |
| слайсов ≥ 50 мс | **0** |

Самые длинные слайсы — `Choreographer#doFrame` 41.5 мс, `DrawFrame` 38.6 мс,
`eglSwapBuffersWithDamageKHR` 33.1 мс, `dequeueBuffer` 32.3 мс. То есть хвост кадров уходит
в отрисовку/обмен буферами с GPU (RenderThread), а не в логику приложения:
`traversal` 27.7 мс и `draw` 27.5 мс встречаются реже и не доминируют.

Это и есть недостающее доказательство причины: при текущих данных и сценарии **блокировок
главного потока > 50 мс нет**, узкое место — не UI-логика. Требование плана «нет block
main-thread > 50 мс на обычных переходах» для прокрутки каталога выполнено.


## 4. Почему не сделано «оптимизаций» из списка

S-006 не выявил ни одного устойчивого bottleneck: постеры, сеть, размер каталога и ветка UI
дали различия меньше разброса между одинаковыми прогонами. По требованию плана решение
выбирается по обнаруженному bottleneck, поэтому спекулятивные правки (кэш картинок, prefetch,
переписывание списков) не вносились — они изменили бы код без доказательства пользы.

Единственный кандидат на проверку остался с прошлого шага: старая View-главная против Compose
(P95 27 vs 20 мс при пересекающихся диапазонах).

## 5. Что остаётся незакрытым

- Пункт «фиксируемая разница на физическом устройстве» проверен (см. §6): устойчивой
  разницы не показано. Это результат измерения, а не подмена эмуляторными числами.
- Не сделаны `frameOverrunMs`/`FrameTimingMetric` (нужен API 31+ и модуль macrobenchmark)

- Разбор main-thread сделан по atrace (§3.1), а не по Perfetto.

## 6. Физический замер PERF-02 (S-065)

Устройство: OnePlus 6T (ONEPLUS_A6013), Android 10 (API 30), 1080×2340, сборка
`com.arny.mobilecinema.benchmark` (non-debuggable, release/R8, подписана debug-ключом).

## 7. Чек-лист S-007 (PERF-02)

| Пункт плана | Статус | Где видно |
|---|---|---|
| SQL ORDER BY/индекс, page 20–40, paging в data/domain | есть | `CatalogPaging.PAGE_SIZE = 24`, сортировка в запросе к DAO, пагинация в `CatalogViewModel` |
| `key` по стабильному id, не индекс | есть | `items(state.items, key = { it.dbId })` |
| `contentType` для разнородных ячеек | добавлено в этом цикле | `MobileCatalogScreen.kt`: `"poster"`, `"loading-more"`, `"genre"` — карточки больше не переиспользуют композицию служебных ячеек |
| Screen-specific state + `collectAsStateWithLifecycle` | есть | `HomeFragment` (3 коллектора), `MobileCatalogFragment` (1) |
| Нет `sort/filter/map` тяжёлого списка в композиции | есть | сортировка/фильтр живут в запросе, не в composable |
| `remember`/`derivedStateOf` только по нужде, без массового `@Immutable` | есть | скрытых кэшей в композиции нет |
| Coil: размер по карточке, кэш, placeholder/error | есть | `AsyncImage` с `fillMaxWidth().aspectRatio(2/3)` — запрос уходит по фактическим ограничениям вёрстки, дефолтный memory+disk cache |
| Не пересоздавать коллекции на каждом тике | есть | прогресс живёт в отдельном потоке/адаптере истории, каталог не перерисовывается |
| Cancel/debounce, никакого блокирующего I/O на main | есть | поиск/обновление в корутинах, debounce в поиске |
| Отдельный child composable для прогресса/таймеров | есть | карточки и строки прогресса — отдельные composable |
| Baseline Profile после стабилизации | **не здесь** | это отдельные шаги плана S-051…S-055 (Macrobenchmark/profile); модуля `:macrobenchmark` и `profileinstaller` в проекте нет, поэтому пункт не подменяется фиктивным профилем |

Приёмка (все четыре пункта):

2. доказательство причины — §3.1 (atrace: 0 слайсов ≥ 50 мс на главном потоке);
3. физический замер — §6 (устойчивой разницы не показано, ограничения описаны);
4. новые ANR — не появились: 0/10 прогонов на телефоне, на эмуляторе `am_anr` не зафиксирован.
