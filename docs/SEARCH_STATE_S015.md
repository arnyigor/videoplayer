# S-015: состояние поиска — одна модель

## Что было

`SearchUiState` держал четыре независимых флага (`isLoadingLocal`, `isLoadingRemote`,
`localError`, `remoteError`) плюс `searched`. «Загрузка» и «пусто» различались только их
комбинацией, а идентификатор запроса был приватным `Int`-счётчиком в ViewModel — в состоянии
его не было, поэтому UI не мог отличить ответ старого запроса.

## Что сделано

1. **`ResultSection`** (`IDLE / LOADING / SUCCESS / EMPTY / ERROR`) и два производных поля
   состояния — `localSection` и `remoteSection`. Экран больше не собирает статус из флагов:
   `renderSourceStatus` читает секции. Заодно различаются «не искали» и «ничего не нашли».
2. **`pendingRequestId: Long`** в состоянии (раньше — приватный счётчик поколений):
   каждый поиск увеличивает id, ответ с чужим id отбрасывается. `loadMore` фиксирует id.
3. **Черновик фильтров не дублируется в состоянии.** Правки фильтров живут в
   `SearchFiltersSheet`, в состояние попадают только по кнопке Apply. Отдельное поле
   `draftFilters` создало бы вторую правду о том же самом — это осознанное отступление от
   формулировки плана, а не пропуск.

## Один ViewModel на поиск

Проверено, что экран поиска обслуживает **один** `SiteSearchViewModel`. `ExtendedSearchViewModel`
остался в проекте, но им никто не пользуется: переходов на `nav_extended_search` в коде нет
(см. `docs/SEARCH_S012_PROGRESS.md`). Удаление мёртвого экрана — отдельная чистка.
